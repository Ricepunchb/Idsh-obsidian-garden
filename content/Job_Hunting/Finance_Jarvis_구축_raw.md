# Finance Jarvis — 포트폴리오 문서

> 한국투자증권(KIS) OpenAPI 기반 **국내 주식·ETF 자동매매 엔진 + AI 포트폴리오 에이전트 + 매매 복기 대시보드**.
> "돈이 걸린 자동화 시스템을 어떻게 안전하게 만들 것인가"를 중심으로 설계한 개인 프로젝트.

저장소: https://github.com/Ricepunchb/Finance_Jarvis
실행 방법과 기능 사용법은 [README](../README.md)에 있고, 이 문서는 **무엇을 왜 그렇게 만들었는지, 무엇이 터졌고 어떻게 고쳤는지**를 다룬다.

**만든 것 세 가지**

1. **자동매매 엔진** — 30분마다 종목별로 손절/트레일링 → 리스크 점검 → 시그널 결합 판단 → 주문 → 체결 대조까지 수행.
2. **AI 포트폴리오 에이전트** — KOSPI·KOSDAQ 전 종목에서 후보를 발굴하고 LLM이 비중 조정·편입/제외를 *제안*. 사람이 승인해야만 반영.
3. **매매 복기 대시보드** — 체결·판단 기록으로 손익을 계산하고, "그날 엔진이 왜 그렇게 판단했는지"를 원본 근거와 함께 다시 본다.

## 2. 문제 정의와 목표

**왜 만들었나.** 개인이 시그널 몇 개로 자동매매를 돌리는 건 어렵지 않다. 어려운 건 그다음이다. 프로세스가 죽었다 살아나면 주문이 중복되지 않는지, API가 일시적으로 실패해도 손절은 작동하는지, LLM이 이상한 제안을 내도 포트폴리오가 망가지지 않는지. 이 프로젝트는 "수익 알고리즘"보다 **"실패했을 때의 동작"을 먼저 설계**하는 것을 목표로 했다.

**설계 원칙 (모든 결정의 기준)**

1. 손실을 줄이는 방향의 동작(손절)은 다른 어떤 제한보다 우선한다.
2. 불확실하면 추측하지 말고 멈춘다 (`UNKNOWN` 상태, 킬스위치).
3. 보조 입력(뉴스·LLM·밸류에이션)이 죽어도 핵심 안전장치는 영향받지 않는다.
4. AI는 제안까지만, 반영은 사람이 한다.
5. 모든 판단은 사후에 재현 가능해야 한다 (판단 시점의 컨텍스트 스냅샷 저장).

## 3. 아키텍처

```
브라우저
  └─ Streamlit ── 복기·분석(읽기 전용) / 자동매매 제어 (화면에는 매매 로직 없음)
        │ HTTP
        ▼
FastAPI 서버
  ├─ TradingEngine (30분 사이클, 종목별 격리)
  │    1. 손절/트레일링 (exit_guard)         ← 가장 먼저
  │    2. 쿨다운·한도·VI 점검 (risk)
  │    3. 매매 판단 (signal_engine)
  │         일봉 지표 + 30분봉 + 뉴스 감성 + 밸류에이션
  │    4. 주문 의도 기록 → KIS 주문 → 체결통보 → 체결 기록
  ├─ PortfolioScheduler (엔진과 별개, 기본 꺼짐)
  │    트리거 → 종목 발굴 → LLM 제안 → 한도 검사 → PROPOSED 저장 → 사람 승인
  └─ analytics (읽기 전용 조회·계산)
        │
   SQLite ── KIS OpenAPI(REST+WS) ── 네이버 금융 / Gemini / CNN
```

- **엔진은 API 서버 프로세스 안에서만 돈다.** 브라우저를 닫아도 계속 돌고, UI는 엔진을 직접 건드리지 않는다.
- **판단·주문 의도·체결·포지션(진입가/고점)을 전부 SQLite에 남긴다.** 재시작하면 KIS 체결내역과 대조해 상태를 복구한다.
- **종목 단위 격리.** 한 종목이 실패해도 사이클은 계속된다.

## 4. 핵심 설계 결정

### 4.1 중복 주문 방지 — 주문 의도 상태머신 + 재시작 대조

- **문제:** KIS는 주문 멱등성 키를 지원하지 않는다. 주문을 보낸 직후 프로세스가 죽으면, 재시작 시 "그 주문이 들어갔는지" 알 방법이 없다. 그냥 다시 보내면 이중 주문.
- **결정:** 주문 전에 `order_intents`에 의도를 먼저 기록(UNIQUE 제약)하고, 재시작 시 PENDING/SUBMITTED 상태인 의도를 KIS 체결내역과 fuzzy match로 대조한다. **일치하는 주문이 2개 이상이면 추측하지 않고 `UNKNOWN`으로 멈춰 사람이 확인**한다.
- **트레이드오프:** 가끔 사람이 개입해야 하지만, 돈이 걸린 시스템에서 "그럴듯한 추측"보다 "멈춤"이 싸다고 판단.
- 이후 주문 POST는 중복 위험 때문에 **재시도하지 않고**, 조회(GET)만 백오프 재시도하도록 구분했다.

### 4.2 손절은 모든 제한보다 먼저, 그리고 제한을 무시한다

- 평단 대비 -7% 전량 매도, 트레일링 익절은 **재주문 쿨다운과 일일 손실 한도를 일부러 우회**한다. 손실을 줄이는 매도가 "신규 매매 제한"에 걸리면 안 되기 때문.
- 다만 VI(변동성 완화장치) 중에는 보류.
- 체결통보 WebSocket이 비정상일 때도 **신규 주문은 막되, 보유 종목의 손절 평가는 계속**한다 (4.5의 장애 경험 이후 추가).

### 4.3 시그널은 방향, 목표 비중 밴드는 상한

초기에는 목표 비중 밴드가 매매 방향을 정하는 저빈도 리밸런싱 구조였다. Phase 4에서 **시그널이 방향·타이밍을 정하고, 밴드는 "과대 비중을 강제로 줄이는 상한"으로만** 남기는 스윙 구조로 재설계했다. 결합 가중치는 일봉 30% / 30분봉 50% / 뉴스 20% / 밸류에이션 20%(없는 시그널은 빼고 재정규화). 뉴스 감성 단독으로는 매매를 시작할 수 없게 막아, LLM 출력 하나가 주문으로 직결되지 않도록 했다.

### 4.4 AI 에이전트: 환각을 구조로 차단하고, 어기면 통째로 버린다

- **환각 티커 차단:** LLM은 사전에 만든 후보 숏리스트 밖의 종목을 낼 수 없고, 후보 자체도 KIS 실재성·VI·종목명 대조 검증을 거친다.
- **한도 위반은 보정하지 않고 전체 반려:** 회전율 20%, 종목당 변화 10%p, 편입·제외 각 2개 등을 넘으면 숫자를 깎아 맞추지 않고 제안 전체를 버린다. 숫자를 임의로 고치면 "LLM이 낸 제안"과 "실제 반영된 안"이 달라져 감사가 안 되기 때문.
- **제안(스케줄러)과 반영(승인)을 분리**하고, 모든 과정을 `rebalance_events` 감사 로그로 남긴다.
- 이후 한도 위반으로 제안이 통째로 반려되는 빈도를 줄이려고, 종목당 최소/최대 비중을 **프롬프트에 명시**했다 (검증은 그대로 유지하고 입력 쪽에서 위반 확률을 낮춤).

### 4.5 데이터 소스가 불안정하다는 전제

네이버·CNN은 비공식 엔드포인트라 언제든 바뀐다. 모든 외부 소스를 "실패하면 그 입력만 빠지고(HOLD/None) 나머지는 계속 도는" 구조로 만들었다. LLM은 `core/llm/base.py` 인터페이스 뒤에 두어 제공자를 교체할 수 있게 했고, 모델 단종(404)·5xx는 폴백 모델이 받는다.

### 4.6 범위를 줄이는 결정: 해외 → 국내 전용

Phase 3에서 미국 주식(거래소별 TR ID, 외화·원화 통합 총자산, 야간장)까지 구현했지만, 해외 수수료 부담(과 정규장 전체 사이클 미검증) 때문에 **`DOMESTIC_ONLY`로 전환**하고 해외 호출 경로를 막았다. 기능을 지운 게 아니라 플래그 뒤로 넣고, 기존 해외 이력은 DB에 보존, 보유분은 일회성 청산 스크립트(`--dry-run` 지원)로 정리했다. "만든 걸 아깝다고 계속 끌고 가지 않는" 판단 사례.

## 5. 트러블슈팅 사례

아래는 대부분 **라이브 모의투자를 돌리며, 그리고 매매 기록을 복기하며** 발견한 문제들이다. 유닛 테스트만으로는 못 잡았을 종류가 많다.

### 5.1 두 종목이 3일 동안 한 번도 매매 신호를 못 받았다 — 예산 배분 버그
- **발견:** 매매 기록을 복기하다 특정 두 종목이 83사이클(3일) 내내 거래가 없음을 확인.
- **원인:** 30분봉 백필은 모의투자 초당 1건 제한 때문에 사이클당 3종목만 처리하는데, 예산을 "처리한 종목 수"만큼 차감했다. 처리 순서가 고정이라 앞쪽 종목이 이미 캐시가 충분해도 예산을 소모했고, 뒤쪽 두 종목은 분봉을 한 번도 못 받았다. 30분봉이 결합 점수의 50%라서 **그 종목들은 임계값을 수학적으로 넘을 수 없는 상태**였다.
- **해결:** `BackfillBudget` 도입 — 실제로 백필이 필요했던 종목만 예산을 소비.
- **배운 점:** 에러 없이 "조용히 아무것도 안 하는" 버그는 로그가 아니라 **결과 기록(복기)**으로만 보인다. 이게 복기 대시보드를 만든 직접적 동기가 됐다.

### 5.2 정지/긴급정지 버튼이 실제로는 아무것도 안 했다
- **원인:** uvicorn 재시작 후 새 엔진 인스턴스는 DB 커넥션이 `None`인데, `stop()/kill()`이 None 가드에서 조용히 성공 응답만 반환. 대시보드에는 죽은 프로세스의 "실행 중"이 남았고, 긴급정지는 주문은 취소하면서 킬스위치는 켜지 않았다.
- **해결:** 커넥션이 없으면 새로 열어서라도 상태를 반드시 기록.
- **배운 점:** 안전 기능에서 "조용한 성공"이 가장 위험하다. 실패는 시끄럽게, 상태 기록은 무조건.

### 5.3 WebSocket이 끊기면 손절까지 멈췄다
- **원인:** 체결통보 WebSocket staleness 게이트가 신규 주문뿐 아니라 손절/트레일링 평가까지 막고 있었고, 끊긴 연결은 수동 재시작 전까지 방치됐다.
- **해결:** 1초→최대 60초 지수 백오프 자동 재연결(메시지 수신 시 초기화, `stop()` 시 대기 중이어도 즉시 취소). 로컬 목 WebSocket 서버로 재연결·지수 증가·즉시 종료 3가지 시나리오를 직접 검증. 이후 게이트도 손절은 통과시키도록 분리.

### 5.4 서머타임 때문에 킬스위치가 오탐으로 발동
- **원인:** 미국장 개장 판정이 고정 KST 시각(22:00)이라 서머타임 기간에 장 시작 전으로 오판 → 주문 거부 연속 → "60초 내 3회 거부" 킬스위치 조건 충족.
- **해결:** 시장 시각을 `America/New_York` 기준으로 판정.
- **배운 점:** 시간대는 오프셋이 아니라 **타임존**으로 다뤄야 한다. 그리고 킬스위치가 설계대로 "정확히 작동"했기 때문에 원인을 빨리 찾을 수 있었다.

### 5.5 서드파티 라이브러리 버그 — pandas_ta의 CCI
- 지표 원시값을 대시보드에 노출하려고 수동 계산과 대조 검증하다가, `pandas_ta` 3.0.6의 `cci()`가 수식 괄호 누락으로 값이 **수백~수천 배 부풀려진다**는 걸 발견. RSI/MACD/볼린저는 수동 계산과 일치함을 확인하고 CCI만 직접 계산으로 대체. 실거래 판단 경로(`compute_technical_signal`)와 표시용(`compute_technical_detail`)은 분리해 매매 로직 영향 차단.

### 5.6 시그널이 0.333에만 몰렸다 — 양자화 문제
- RSI/BB는 중립 구간에서 항상 0표, MACD는 항상 ±1표인 이분법 투표라 score가 `{0, ±1/3, ±2/3, ±1}`에만 존재했다. RSI는 50 중심 선형보간, MACD는 히스토그램 z-score에 tanh, BB는 %B로 **연속값**을 내도록 바꾸되 기존 임계값이 여전히 ±1 포화점이 되도록 보정.

### 5.7 평단 근처 고점에서 손실 익절이 나갔다 — 트레일링 재설계
- 고점 대비 고정 -5% 트레일링은, 평단보다 조금 오른 고점에서도 "익절"이라는 이름으로 손실 청산을 만들었다. 고점이 평단보다 충분히 올랐을 때만 **무장**하고, 폭은 **ATR 기반(2.5×ATR%, 3~12%)**으로 변동성에 맞추도록 변경(ATR 불가 시 -5% 폴백).
- 같은 시기에 전량 청산된 종목의 포지션이 초기화되지 않아 **재진입 시 옛 고점이 이월**되는 버그도 복기에서 발견해 수정.

### 5.8 KIS 호출 제한(EGW00201)
- 모의투자 초당 호출 제한 초과로 조회가 간헐 실패. 기존 제한기를 **호출 시작 간 최소 간격(모의 1.2초) 방식 제한기**로 교체하고, GET만 백오프 재시도(주문 POST는 4.1의 이유로 재시도 금지).
- 초기에는 토큰 무기한 캐시 버그(만료 미처리)와 초당 호출 제한 누락도 함께 잡았다.

### 5.9 "정상인데 에러처럼 보이는" UX 문제들
- reconciliation·WebSocket 연결·주문 취소는 응답 전에 수십 초가 걸리는데 대시보드 기본 타임아웃 10초에 걸려 **정상 완료됐는데도 트레이스백이 표시**됨. 느린 엔드포인트만 60초로 늘리고, 타임아웃 시에는 "새로고침해서 확인" 안내만 보이게 처리.
- 모의투자 시세 API가 종목명을 빈 값으로 주는 경우가 있어, "종목명이 있어야 실재 종목"으로 본 검증이 **보유 중인 종목까지 전부 반려**. 실재성은 가격 조회 성공으로, 이름 대조(환각 방지)는 이름이 있을 때만 하도록 분리.
- DataFrame 숫자 컬럼에 `"-"` 문자열을 섞어 pyarrow `ArrowInvalid` 발생 → `None`으로 교체.

5.1 같은 버그를 계기로 읽기 전용 분석 대시보드를 따로 만들었다.

- 한국식 색상(상승=빨강) 기본, 토글로 반전.

## 7. 검증 방식과 한계

**어떻게 검증했나**
- 안전 로직(밴드·쿨다운·손절·한도·reconciliation·국내 전용 차단·손익 계산)은 유닛 테스트 86개.
- KIS REST/WebSocket, Gemini 호출은 **실제 모의투자 서버와 실제 API로** 라이브 검증 (모델명 만료, 구조화 출력 스키마 제약, 장중 KIS 일시 오류, Gemini 503이 각각 사이클 격리·페일세이프로 흡수되는 것까지 확인).
- 커밋 메시지에 "무엇을 검증했고 무엇은 못 했는지"를 분리해 기록.

**한계 (숨기지 않고 적어둔 것)**
- **수익률 검증이 없다.** 기능별 검증은 했지만 여러 날 연속 운영·백테스트 기반의 성과 검증은 하지 않았다. 이 프로젝트가 보여주는 것은 "수익이 나는 전략"이 아니라 "안전하게 운영 가능한 구조"다.
- 휴장일 캘린더 없음, 수수료·세금을 판단에 미반영(잦은 신호 반전 시 비용 누적 가능).
- 비공식 API(네이버·CNN) 의존.
- 미국 주식 정규장 실주문 전체 사이클은 미검증 (이후 국내 전용으로 전환).

**다음에 한다면**
- 휴장일 캘린더와 수수료·세금을 판단·손익에 반영, 백테스트로 시그널 가중치 근거 확보.
- Fear & Greed를 현재는 LLM 참고 맥락으로만 쓰는데, 역발상/추세추종 방향을 정한 뒤 리스크 파라미터로 확장.
- 엔진 사이클·주문 흐름에 대한 메트릭/알림.

## 9. 이 프로젝트에서 배운 것

1. **안전 설계는 기능이 아니라 실패 모드 목록에서 나온다.** 중복 주문, 조용한 실패, 외부 의존성 장애, 시간대, 재시작 — 각각을 "어떻게 멈출 것인가"로 먼저 정리했다.
2. **LLM은 신뢰 경계 밖에 둔다.** 출력은 후보 제한·한도 검사·사람 승인의 세 겹을 통과해야 효력이 생긴다. 보정이 아니라 반려, 자동 반영이 아니라 제안.
3. **라이브 환경이 테스트가 못 잡는 버그를 준다.** 모의투자의 제약(초당 1건, 빈 종목명, 매도가능수량 미지원)이 오히려 설계를 단단하게 했다.
4. **기록해야 고칠 수 있다.** 판단 스냅샷과 체결 기록이 복기 대시보드의 전제였고, 복기가 최고의 버그 탐지기였다.
5. **범위를 줄일 줄 알아야 한다.** 해외 지원을 플래그 뒤로 접고 국내 품질에 집중한 결정.

## 10. 이력서·면접용 문구

**이력서 불릿 (골라 쓰기)**
- KIS OpenAPI 기반 국내 주식·ETF 자동매매 엔진 설계·구현 (Python, FastAPI, asyncio, SQLite). 주문 멱등성 키가 없는 환경에서 **주문 의도 상태머신 + 재시작 시 체결내역 대조**로 중복 주문을 방지하고, 모호한 경우 `UNKNOWN`으로 정지하도록 설계.
- 손절·트레일링 익절을 쿨다운/손실 한도보다 우선 평가하는 리스크 계층, 체결통보 WebSocket 지수 백오프 재연결, 시장 이상 감지 킬스위치 구현.
- Gemini 기반 포트폴리오 에이전트 개발: 후보 숏리스트 제한·KIS 실재성 검증으로 환각 티커를 구조적으로 차단하고, 회전율·종목당 변화폭 한도 위반 시 제안 전체를 반려, 승인은 사람이 하는 감사 가능한 워크플로 구성.
- 매매 기록 복기용 분석 대시보드를 만들어 **3일간 신호를 못 받던 종목 버그(백필 예산 편중)** 등 에러 없이 조용히 실패하던 문제를 발견·수정.
- pytest 86개 테스트, 실제 모의투자 서버 라이브 검증, 서드파티(pandas_ta) 지표 버그를 수동 계산 대조로 발견해 대체.

**30초 소개**
> 한국투자증권 API로 국내 주식 자동매매 엔진을 만든 개인 프로젝트입니다. 수익 전략보다 "실패했을 때 어떻게 동작하는가"에 집중했습니다. 주문 멱등성 키가 없는 API에서 중복 주문을 막는 상태머신, 손절을 모든 제한보다 우선하는 리스크 계층, LLM 제안을 한도 검사와 사람 승인 뒤에만 반영하는 구조가 핵심이고, 매매 기록을 복기하는 대시보드를 만들어 조용히 실패하던 버그들을 찾아 고쳤습니다.

**예상 질문 → 답변 포인트**
| 질문 | 포인트 |
|---|---|
| 왜 LLM 제안을 자동 반영하지 않았나? | 돈이 걸린 결정에서 LLM 출력은 신뢰 경계 밖. 후보 제한 + 한도 검사 + 사람 승인 3겹, 보정 대신 전체 반려해야 감사 가능 (4.4) |
| 재시작 때 주문이 들어갔는지 어떻게 아나? | `order_intents` 선기록 + KIS 체결내역 fuzzy match, 2건 이상 일치 시 `UNKNOWN` 정지 (4.1) |
| 가장 어려웠던 버그는? | 3일간 두 종목이 신호를 못 받던 백필 예산 편중. 에러가 없어 복기로만 발견 (5.1) |
| 수익률은? | 검증하지 않았다. 이 프로젝트의 목표는 안전한 운영 구조이며, 성과 검증은 다음 과제 (7) |
| 직접 해본 의사결정은? | 시그널 주도 구조로 재설계(4.3), 해외 → 국내 전용 범위 축소(4.6), 트레일링 ATR 재설계(5.7) |
